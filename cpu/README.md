# CPU 스케줄링 탐색기

세 작업이 하나의 CPU를 나누는 과정을 레슨별로 실행·예측·비교하는 한국어 학습 앱입니다. 원래 프로젝트에 대한 런타임 의존성은 없습니다.

## 실행

이 탐색기는 [탐색기 모음](../README.md)의 한 페이지입니다. 저장소 루트에서 `npm run dev`를 실행한 뒤 <http://127.0.0.1:5173/cpu/>을 엽니다. 검사는 루트의 `npm test`로 모든 탐색기를 함께 실행합니다.

## 레슨

왼쪽 레슨 레일(`src/components/shell/lesson-rail.tsx`)에서 고릅니다. 1280px 미만에서는 상단 `레슨` 키로 여는 서랍입니다. 레슨은 URL로 바뀝니다(`/cpu/`, `/cpu/?lesson=sjf`, `/cpu/?lesson=srtf`). 데이터와 내용은 `src/explorers/cpu/lessons.ts`, CPU만 쓰는 레슨의 장면·예측·해설은 `policy-lesson.ts`, 엔진의 SJF/SRTF는 `engine.ts`에 있습니다. 근거: OSTEP 7장(7.3 FIFO, 7.4 SJF, 7.5 STCF).

| 레슨 | 질문 | 작업(도착 · CPU) | 두 방식 | 검산 |
| --- | --- | --- | --- | --- |
| 01 RR과 FCFS | 빠른 응답과 빠른 완료는 같은 뜻일까요? | 아래 대표 시나리오(입출력 포함) | 라운드 로빈(할당량 1~5 ms) · FCFS | 아래 표 |
| 02 SJF와 FCFS | 짧은 작업을 먼저 하면 평균 대기는 얼마나 줄까요? | P1 0·8, P2 0·2, P3 0·5 | FCFS · SJF(비선점) | 평균 대기 6 → 3 ms, 평균 반환 11 → 8 ms, 전체 완료 둘 다 15 ms |
| 03 SRTF와 SJF | 긴 작업을 멈추고 짧은 작업에 CPU를 주면 무엇이 좋아질까요? | P1 0·8, P2 1·2, P3 2·3 | SJF · SRTF(선점, STCF) | 평균 대기 5 → 2 ms, 평균 반환 9.33 → 6.33 ms, 문맥 교환 2 → 3회; 1 ms에 P2가 P1을 선점, 2 ms에 P3(3 ms)는 남은 1 ms의 P2를 선점하지 못함 |

- SJF·SRTF는 준비 큐(도착 순서 유지)에서 남은 CPU 시간이 가장 짧은 작업을 고르고, 같으면 먼저 줄을 선 작업이 우선합니다. SRTF는 작업이 들어올 때마다 비교해 더 짧을 때만 선점하며, 선점하지 않은 경우도 `keep` 결정으로 기록해 예측 문제로 씁니다. 두 방식 모두 CPU 시간을 미리 안다고 가정합니다(OSTEP 7.4).
- 시작 화면은 t=-1(`preFrame`)로, 아무도 도착·배정되지 않은 상태입니다. 그래서 0 ms의 첫 선택도 예측할 수 있습니다.
- 진도는 레슨마다 `createProgress(progressIdFor("cpu", LESSONS, id), …)`로 저장합니다(01은 기존 `cpu`). 정리의 링크는 다음 레슨, 마지막 레슨은 다음 실험으로 이어집니다.
- 04(MLFQ 또는 우선순위+에이징)는 만들지 않았습니다. 여러 큐와 우선순위 변화를 보여 주려면 장면을 새로 설계해야 해서, 어설프게 넣기보다 생략했습니다.

## 레슨 01 · 대표 시나리오

| 작업 | 도착 | 작업 순서 |
| --- | --- | --- |
| P1 · 문서 미리보기 | 0 ms | CPU 5 → 입출력 4 → CPU 3 |
| P2 · 파일 검색 | 1 ms | CPU 2 → 입출력 3 → CPU 2 |
| P3 · 수식 계산 | 2 ms | CPU 4 |

라운드 로빈의 시간 할당량을 1~5 ms로 변경하거나 선입선처리(FCFS)로 바꿀 수 있습니다. 입력이 바뀌면 준비 큐·장치 상태·애니메이션·시간표·설명·통계를 같은 시뮬레이션 결과에서 다시 계산합니다.

대표 RR 2 ms 실행 순서:

```text
P1 0–2 → P2 2–4 → P3 4–6 → P1 6–8
→ P3 8–10 → P2 10–12 → P1 12–13
→ CPU 유휴 13–17 → P1 17–19 → P1 19–20
```

| 검산 지표 | RR · 2 ms | FCFS |
| --- | ---: | ---: |
| 평균 최초 응답 | 1 ms | 3 ms |
| 평균 대기 시간(준비 큐) | 5.33 ms | 5 ms |
| 평균 반환 시간 | 13 ms | 12.67 ms |
| 전체 완료 시각 | 20 ms | 16 ms |
| CPU 활용률 | 80% | 100% |
| 문맥 교환(작업 전환) | 6회 | 4회 |

학습의 핵심 질문은 **빠른 응답과 빠른 완료는 같은 뜻일까요?**입니다. t=7의 입출력 복귀는 이미 기다리는 P3를 추월하지 않습니다. t=13~17에는 P1의 입출력을 기다리므로 CPU가 쉬지만, 이 시간은 대기 시간(준비 큐)으로 세지 않습니다. RR에서 P1의 첫 입출력이 5 ms(FCFS)에서 13 ms로 늦어져 CPU 실행과 겹치지 못하기 때문이며, 문맥 교환 비용(0 ms) 때문이 아닙니다. FCFS가 늘 유리한 것은 아닙니다. 이 시나리오의 FCFS에서도 P2·P3는 P1의 5 ms CPU 구간 뒤에서 4 ms, 5 ms를 기다립니다(호위 효과, convoy effect). 할당량 5 ms처럼 두 실행이 같으면 이 문장은 비교 화면에 나오지 않습니다.

## 학습 흐름

탐색기 모음의 공통 학습 모델(`docs/DESIGN.md` → Learning model, 문구는 `src/lib/lesson-kit.ts`의 `LABELS`)을 따릅니다.

- **목표**: 재생 전 시작 화면은 질문 "빠른 응답과 빠른 완료는 같은 뜻일까요?", 시나리오 설명, `학습 목표: …` 한 줄과 용어(최초 응답·반환 시간·준비 큐)만 보여 줍니다. 실행 결과는 미리 보여 주지 않습니다.
- **관찰**: `핵심 장면에서 멈추기`를 켜면 핵심 장면(RR 2 ms 7개, FCFS 5개)마다 멈춥니다. 재생 키는 `학습 시작 / 이어서 재생 / 일시정지 / 다시 재생`, `이번 사건 다시 보기`로 방금 시각의 이동을 다시 봅니다.
- **예측**: 다음 CPU 배정 직전에 멈추고, 끝나지 않은 모든 작업(실행 중인 작업 포함)을 선택지로 줍니다. 각 선택지에는 그 오해("도착하면 바로 실행된다", "입출력 복귀가 선점한다", "할당량이 남으면 계속 실행된다" 등)에 맞는 이유가 붙습니다. 이어지는 숫자 예측은 최초 응답이나 이번 차례의 CPU 사용 시간을 묻고, 정답 위치는 결정마다 다르며 할당량을 넘는 값은 내지 않습니다. 할당량 1 ms에서는 매 차례가 1 ms이므로 사용 시간 질문을 생략합니다.
- **확인 → 설명**: `실제로 확인 →`이 그 배정을 재생합니다. 해설 탭은 핵심 장면 번호·제목·본문, `이번 사건`, 단계마다 바뀌는 `핵심` 메모를 보여 줍니다.
- **비교**: `두 방식 비교`(끝에서는 `결과 비교 →`)는 같은 입력을 다른 방식으로 실행한 두 시간표·지표와 할당량 1~5 ms 결과를 보여 줍니다.
- **정리**: 마지막 장면 뒤 해설에 핵심 정리 3개, 장면 없이 푸는 확인 문제 2개(선택지마다 이유), 학습 진도, 다음 실험 링크가 이어집니다. 진도는 `createProgress("cpu", { scenes: 7, recall: 2 })`로 저장합니다.

## 조작

- 재생·일시정지, 1 ms 앞뒤 이동, 다음 사건, 초기화, 0.5×/1×/2× 속도
- 준비 큐·CPU·입출력 장치 바로 아래에 작업 카드를 배치합니다. 실선은 CPU 배정·입출력 요청, 점선은 할당량 만료·입출력 완료 후 준비 큐 복귀를 나타냅니다. 큐의 빈 마지막 칸은 다음 작업이 합류할 자리입니다.
- 이동할 때 카드는 작업 번호 표식으로 접히고, 표시된 경로를 따라 목적지에서 다시 펼쳐집니다. 같은 시각의 사건도 순서대로 보여 주며, 모든 이동이 끝날 때까지 시뮬레이션 시각을 진행하지 않습니다.
- 기본 재생은 핵심 장면에서 자동으로 멈춥니다. 해설을 읽고 다시 재생하거나, `핵심 장면에서 멈추기`를 꺼 연속으로 볼 수 있습니다. 개념 해설은 장면 동안 유지되고 사건·숫자만 현재 시각에 맞춰 바뀝니다.
- 시간 슬라이더·시간표 눈금·사건 기록·핵심 장면을 눌러 탐색
- 시간표·사건 기록·작업별 지표는 하단의 관찰 기록 탭에서 전환합니다.
- 작업을 누르면 현재 CPU·입출력 구간, 구간별 진행량, CPU 실행·준비 큐 대기·입출력 대기의 시간 분해를 살펴볼 수 있습니다. 완료 전 반환 시간은 미리 표시하지 않습니다.
- 다음 CPU 배정 직전의 현재 작업(남은 할당량·구간, FCFS는 남은 구간)·준비 큐·새로 들어올 작업을 근거로 다음 차례를 예측하고, 이어서 숫자로 예측합니다. 숫자 질문에는 선택된 작업의 이번 CPU 구간이 몇 ms 남았는지 함께 보여 줍니다.
- 두 알고리즘의 전체 시간표와 6개 지표 비교. 할당량별 줄은 전체 완료가 입출력 겹침에 따라 달라져 할당량과 단조 관계가 아님을 밝힙니다.
- Space: 재생·정지 / ←·→: 1 ms 이동 / R: 초기화
- 모바일 배치, 밝은·어두운 테마, 동작 줄이기 설정 지원

## 모델의 범위

CPU는 하나, 입출력은 서로 독립적으로 진행되며 문맥 교환 비용은 0 ms로 가정합니다. 같은 경계 시각에는 CPU 구간 종료를 처리한 뒤 도착·입출력 복귀 작업을 입력 순서대로 준비 큐에 넣고, 시간 할당량이 끝난 작업을 마지막에 넣습니다. 이것은 동시 사건을 재현하기 위한 이 모델의 규칙이며 모든 운영체제의 규칙이라는 뜻은 아닙니다.

프레임 t는 경계 사건 처리 후, `[t, t+1)` 실행 전의 상태입니다. 최초 응답은 첫 실행−도착, 반환 시간은 완료−도착, 대기 시간(준비 큐)은 준비 큐에 머문 누적 시간입니다. 문맥 교환(작업 전환)은 서로 다른 작업 사이만 세고 최초 배정·유휴 진입·같은 작업의 재배정은 제외합니다.

실제 운영체제를 구동하거나 실제 실행 시간을 측정하는 앱은 아닙니다. 같은 작업을 동일한 규칙으로 재현하는 교육용 시뮬레이터입니다.
