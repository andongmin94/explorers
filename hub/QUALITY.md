# 탐색기 학습 품질 검수

2026년 11월 11일 통합 실행본 기준. 여섯 탐색기와 트랜잭션의 교착 상태 화면까지 일곱 화면을 1280×720과 390×844에서 열었다. 대표 장면은 재생, 다음, 단계 바로가기와 완료 화면으로 확인했고, 계산 결과는 각 앱의 모델과 대조했다. 기존 테스트 70개는 모두 통과했다. 프로토콜은 14개 수업의 구성을 확인하고 HTTP·TCP의 화면과 TLS의 설명을 표본 검수했다. 215개 패킷 행을 전부 수동 재생한 결과는 아니다.

| --- | --- | --- |
| 프로토콜 | 클라이언트·라우터·서버 사이의 이동을 네트워크 그림에서 보고, 시퀀스와 패킷 표에서 송수신 순서를 확인할 수 있다. 14개 수업, 78단계가 구현돼 있다. | TCP에서 수신자가 관측한 빈 구간과 송신자가 손실을 판단한 시점을 구분해야 한다. |

## 수정 순서와 확인 방법

1. **디스크의 첫 단계 이동을 복구한다.** 새로 열어 기본 FCFS에서 ‘3 방향 변화’를 바로 누른다. 화면은 3/8과 ‘처리 완료’를 표시하지만 헤드는 53, 누적은 0칸, 기록도 0건이다. 시작 상태의 요청이 비어 있는데 요청 ID를 읽면서 화면 갱신이 중단된다. 이 시점의 올바른 경로는 53 → 98 → 183 → 37, 누적은 276칸이다. 첫 요청을 실제 재생한 뒤에는 같은 오류가 나지 않는다. 고친 뒤에는 새로 연 상태에서 바로가기와 슬라이더를 각각 움직여 장치·카운터·기록이 같은 요청을 가리키는지 확인한다. [재현 화면](disk-seek-issue.jpg) · [디스크 화면 갱신](../disk-scheduling-explorer/src/main.js#L99)

2. **TCP의 손실 판단과 학습 완료 판정을 바로잡는다.** TCP 4→5단계는 SACK가 붙은 중복 ACK 한 개를 보낸 뒤 곧바로 첫 세그먼트를 재전송한다. SACK가 알려주는 것은 도착한 바이트 범위다. 그 시점에서 빈 구간은 지연이나 순서 뒤바뀜으로도 설명된다. 고전적인 빠른 재전송을 가르칠 경우 세 번째 중복 ACK까지, 시간 기반 복구를 가르칠 경우 어떤 시간 조건을 충족했는지 장면에 표현해야 한다. 별도로 새 HTTP 수업에서 마지막 ‘페이지 렌더링’만 골라 끝까지 진행해도 건너뛴 단계까지 모두 완료로 저장된다. 현재 위치와 실제 본 단계를 구분해야 한다. [TCP 장면](../protocol-explorer-source/src/lessons/tcp.js#L275) · [진도 저장](../protocol-explorer-source/src/progress.js#L35) · [RFC 5681 §3.2](https://www.rfc-editor.org/rfc/rfc5681.html#section-3.2)

3. **메모리의 교체 과정을 끝까지 보여준다.** FIFO에서 ‘4번째 A’로 이동해 ‘다음 접근’을 두 번 빠르게 누르면, 5번째가 처리 중인 상태에서 6번째 완료 상태로 바로 바뀐다. 한 접근의 애니메이션이 끝날 때까지 다음 입력을 잠그거나 다음 접근 한 건을 예약하면 된다. 예측 문제는 같은 4번째 장면 왼쪽의 ‘다음 후보’ 표시를 답안 선택 뒤에 보여주면, 학습자가 적재·사용 순서를 보고 직접 고를 수 있다. 조회 화살표의 설명에는 페이지 테이블에서 상주 여부를 확인한다는 점도 밝혀두는 편이 정확하다. 현재 문구는 RAM 프레임 셋을 직접 뒤지는 것으로 읽힌다. [입력 처리](../memory-explorer/src/main.js#L243) · [교체 후보](../memory-explorer/src/main.js#L148) · [조회 장면](../memory-explorer/src/scene.js#L583) · [OSTEP 21장](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-beyondphys.pdf)

4. **CPU 비교 문구를 실제 실행표에서 결정한다.** RR 할당량을 5ms로 두고 ‘실행 결과 비교’를 연다. 두 방식 모두 P1 → P2 → P3 → P1 → P2로 실행되고, 평균 최초 응답 3ms, 평균 준비 큐 대기 5ms, 전체 완료 16ms다. 이 조건은 모든 CPU 구간이 할당량 안에 끝나서 두 방식이 같아지는 좋은 반례다. 기본 2ms에서는 전체 완료가 RR 20ms, FCFS 16ms로 달라지므로 이 차이도 함께 확인한다. [비교 해설](../cpu-scheduling-explorer/src/main.js#L458)

5. **Git은 충돌 발생과 해결 등록을 구분한다.** 9번째 사건에서 작업 파일에는 충돌 표식이 생기고 인덱스에는 공통 조상·현재 브랜치·병합 대상 세 버전이 보관된다. 현재 세 토큰의 이동 목적지는 모두 작업 파일이다. 두 영역이 함께 바뀌는 순간을 연결해 보여줄 필요가 있다. ‘main 문장 유지’로 해결한 경우에는 git add 뒤 HEAD와 다른 파일 내용이 0개여도 충돌 처리가 끝나고 두 부모 커밋을 만들 수 있다. 11번째 장면에 이를 표시하면 ‘해결 등록’의 의미가 분명해진다. 390px에서는 해결 카드가 장면 아래에 있는데도 안내가 ‘오른쪽’을 가리킨다. ‘해결안 선택’ 버튼으로 실제 이동할 수 있으므로 안내에서도 그 버튼명을 쓰면 된다. [충돌 애니메이션](../git-explorer/src/scene.js#L399) · [스테이징 표시](../git-explorer/src/scene.js#L237) · [모바일 안내](../git-explorer/src/main.js#L180)

6. **트랜잭션 기록에서 새 요청과 재개를 구분한다.** 재고 갱신의 마지막 단계에서 ‘SQL 기록 11’을 연다. 11개 사건 중 새로 발행한 SQL은 8개이고, 나머지는 앱 계산 2회와 대기하던 SQL 재개 1회다. 탭을 ‘사건 기록’으로 바꾸고 재개 행에 원래 요청을 연결하면 된다. 일반 읽기의 최종 재고 9, 잠금 읽기의 8, 교착 해소 뒤 A 9·B 19와 커밋 1회·롤백 1회는 모두 모델과 일치했다. [기록 집계](../transaction-explorer/src/main.js#L234) · [PostgreSQL 교착 상태](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-DEADLOCKS)

추가로 프로토콜의 ‘패킷을 하나씩’ 안내는 실제 조작 단위와 다르다. TCP에서 여덟 번 진행했을 때 표에 추가된 패킷은 각각 0·0·1·1·1·1·1·2개였다. ‘다음 장면’으로 안내하거나 패킷 한 개씩 멈추는 동작을 제공하면 된다. TLS 수업의 ‘ServerHello 이후 모든 바이트가 암호화된다’도 같은 예제의 평문 호환용 ChangeCipherSpec 예외에 맞춰 범위를 좁혀야 한다.
