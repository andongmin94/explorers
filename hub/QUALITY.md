# 그림과 움직임만으로 본 탐색기 학습 품질

2026년 11월 11일 통합본을 Chromium에서 일반 속도로 재생했다. 중앙 장면 안의 장치 라벨, 카드, 말풍선은 그대로 읽고 바깥 단계 해설과 기록 표를 가렸다. 이동 전·이동 중·도착 후의 장면을 본 다음 해설과 대조했다. 기본 화면은 1440×900이고 LRU, 디스크의 인접 트랙, 교착 해소, Git 브랜치 전환은 390×844에서도 살폈다. 초보 학습자 대상 실험 없이 화면에서 관측할 수 있는 단서를 기준으로 평가했다. [여섯 장면 실제 캡처](scene-comparison.jpg)

## 먼저 고칠 세 장면

| 순서 | 재현과 관측 | 바꿀 부분 |
| --- | --- | --- |
| 1. CPU · FCFS 8→9ms | P1이 SSD에서 준비 큐로 복귀한다. SSD에는 녹색 P2 카드와 ‘입출력 1ms 남음’이 보이는데, 그 바로 위 슬롯에는 약 0.6초 동안 ‘입출력 요청 없음’도 보인다. | 남은 입출력 작업이 0개일 때만 빈 상태 문구를 표시한다. |
| 2. 트랜잭션 · 일반 SELECT 10→11번 | T1이 재고 9를 확정했다. T2 장치에는 예전에 읽은 10과 거기서 계산한 9가 남아 있다. T2에서 DB로 가는 토큰에는 ‘쓰기 재개’만 적히고 마지막은 ‘9 → 9 확정’이다. 두 주문이 모두 커밋된 사실은 보이지만 한 번의 차감이 사라진 이유는 여러 카드의 숫자를 직접 맞춰야 읽힌다. | T2의 계산값이 ‘재고 ← 9’로 DB까지 이동하게 한다. 도착 순간 DB의 기존 9와 짝지어 보여 준다. ‘읽기부터 잠금’에서 T2가 9를 읽어 8을 쓰는 장면에도 같은 표현을 쓴다. |
| 3. 프로토콜 · FTP 3→6단계 | 패킷 색과 화살표로 RETR 명령과 DATA의 방향은 읽힌다. 파일을 받은 뒤 FIN → 226 → QUIT → 221이 오갈 때는 모두 같은 장치와 경로를 쓴다. FIN이 데이터 연결만 닫았고 제어 연결은 살아 있어서 226과 QUIT을 주고받는다는 상태가 장치에 남지 않는다. | 서버에 ‘제어 21’과 ‘데이터 50069’ 포트를 표시한다. 패킷이 쓴 포트를 켜고 FIN 때 데이터 쪽만 닫는다. |

## 다음으로 다듬을 세 장면

| 순서 | 재현과 관측 | 바꿀 부분 |
| --- | --- | --- |
| 4. 메모리 · LRU 8번째 E | A는 1번에 적재해 6번에 사용했고, D는 5번에 적재해 5번에 사용했다. B의 마지막 사용은 7번이다. D의 테두리는 굵어지지만 ‘적재’와 ‘사용’ 숫자가 같은 비중이라 왜 가장 먼저 들어온 A를 남기는지 찾아 읽어야 한다. 5번째 D에서 FIFO는 A, LRU는 B를 선택할 때도 마찬가지였다. | 예측을 마치고 교체 대상을 결정하는 순간에만 FIFO는 적재 시각, LRU는 마지막 사용 시각을 강조한다. 프레임 위치는 유지한다. |
| 5. 디스크 · SSTF 세 번째 요청 | 헤드 67에서 37까지 30칸, 98까지 31칸이다. 큐에는 둘 다 있지만 37에만 테두리가 생기고 플래터의 다른 후보에는 거리나 번호가 없다. 1칸 차이로 37을 택한 이유는 직접 뺄셈해야 알 수 있다. | 선택하는 순간 두 트랙과 헤드 사이에 30칸·31칸을 잠깐 표시한다. FCFS 마지막 65→67은 모바일에서 헤드 끝이 약 0.46px 움직이므로 짧은 거리 표시는 이 장면에도 도움이 된다. |
| 6. Git · 4→5번 main 전환 | ‘파일 복원’ 카드가 C0에서 작업 파일로 간다. 도착하면 스테이징의 제목과 기준 커밋도 C1에서 C0의 내용으로 바뀌지만 스테이징으로 이어지는 동작은 없다. 390px에서도 세 영역은 화면 안에 들어왔다. | 도착할 때 작업 파일·스테이징의 바뀐 제목 줄을 함께 강조해 C0에서 두 곳을 갱신했다는 관계를 보여 준다. |

## 다른 장면에서 읽힌 것

- **프로토콜** — ICMP에서 TTL 1·2·13의 응답은 각각 집 라우터, 두 번째 홉, 서버에서 출발했다. HTTPS는 자물쇠 안의 GET과 바깥의 암호화된 바이트가 같이 움직였다. IMAP의 새 메일 도착 → 서버 발신 알림도 읽혔다. 다만 POP3에서 DELE 예약 후 QUIT으로 서버 복사본을 지운 결과와 IMAP에서 읽은 메일을 서버에 보관한 결과는 말풍선이 사라지면 비교하기 어렵다. 두 장치에 같은 메일 번호를 남겨 두면 차이가 보인다. SSH는 p·w·d와 에코가 왕복하고 서버의 출력이 돌아오는 방향은 읽혔다. 응답이 도착해도 노트북 화면에 명령이나 출력이 누적되지는 않는다.
- **CPU·메모리** — FCFS에서 9·10ms에 준비 큐로 복귀한 P1·P2는 P3가 11ms에 작업을 마칠 때까지 기다린다. RR 할당량 5ms에서는 작업의 현재 CPU 구간과 할당량이 따로 표시된다. 메모리는 교체 중에도 F0·F1·F2가 같은 자리에 있어서 프레임과 옮겨지는 페이지를 구별할 수 있다.
- **트랜잭션·디스크** — 교착 해소 뒤 T1의 선이 A·B 두 행에 닿고, 두 미확정 값 9·19가 한 커밋에 확정된다. 디스크 FCFS 3번째의 183→37은 팔이 크게 되돌아가 이동 방향의 반전을 볼 수 있다.
- **Git** — 첫 분기 때 C0 하나에 브랜치 이름이 둘 붙고, 첫 편집 때 작업 파일의 제목만 달라진다. 충돌을 main 문장으로 해결하면 등록 후 HEAD와 다른 파일 0개, feature 문장을 선택하면 1개다. 두 경우 모두 C3에 두 부모가 연결돼 파일 내용의 선택과 이력 보존을 구별할 수 있었다.

이번 검수 대상은 위 장면의 일반 재생과 명시한 화면 크기다. 제품 소스 변경 없이 기존 통합본으로 관찰했다.
