# 모바일 재생·정지·배속·되감기 검수

통합본을 터치 방식의 모바일 Chromium에서 재생했다. 해설을 가리고 이동 카드와 장치의 숫자를 먼저 봤다. 그 뒤 기록과 대조하고, 같은 사건에 직접 진입한 상태와 되감은 상태를 비교했다. 화면 폭은 320·390px, 높이는 568·844px를 주로 사용했다. 프로토콜의 320px 화면은 높이 690px다. [재현 화면 비교](scene-comparison.jpg)

## 먼저 고칠 문제

| 순서 | 재현 | 관찰 |
| --- | --- | --- |
| 1 | 프로토콜 · UDP 3단계 ‘도중에 손실’. VOICE 6이 출발하자마자 정지 | 그림에 6만 떠 있고 7·8은 발신 전이다. 같은 순간 패킷 기록은 6·7·8을 모두 ‘현재’로 처리하고 7의 손실까지 표시한다. 7을 눌러 상세 정보도 열 수 있다. 두 폭에서 재현했다. 6·7·8의 기록을 각각의 출발 및 손실 시점과 맞춰야 한다. |
| 2 | 프로토콜 · ICMP 경로 추적에서 정지 후 ‘다음 사건’. HTTPS와 SMTP에서도 같은 조작 | ‘재생’ 버튼이 보이지만 패킷은 움직인다. ICMP 7번 카드가 이동하는 중 주 버튼을 한 번 누르면 연속 재생으로 바뀌고, 두 번째 눌러야 실제로 정지한다. 또 정지 후 ‘이전 단계’를 누르면 이전 단계부터 다시 움직여 사용자가 한 번 더 멈춰야 한다. |
| 3 | CPU · RR 4ms에서 9→10ms, Git · 충돌 비교 9번째의 C2 이동을 보며 정지 | 320×568에서 CPU 정지 버튼 위쪽은 화면 좌표 y=752였다. 버튼이 보일 만큼만 내려 누르면 P1은 진행률 46%에 멈췄지만 카드 전체가 y=−42…−8로 사라졌다. Git C2 카드도 최소 스크롤로 정지하면 320px에서 y=−310…−287, 390px에서도 y=−34…−11이었다. 디스크는 320px FCFS 3번째에서 버튼을 전부 보려면 최소 68px, 트랜잭션은 잠금 읽기 예측 직후 116px 내려야 했다. |
| 4 | 메모리 · LRU 7번째 B, 트랜잭션 · 잠금 읽기 11번째와 교착 9번째, Git · 충돌 비교 9번째에서 배속 변경 | 버튼은 즉시 바뀌지만 현재 사건에 남은 이동은 이전 속도로 재생된다. 메모리에서 2×를 누른 뒤 B 적재는 875ms, 같은 사건을 처음부터 2×로 실행하면 438ms였다. 트랜잭션의 커밋 응답은 554ms와 277ms, Git에서 다음으로 출발하는 C1 카드도 762ms와 381ms였다. 진행 중과 정지 중 변경 모두 확인했다. CPU와 디스크에서는 같은 이동 도중 배속이 바뀌었다. |
| 5 | 트랜잭션 · 잠금 읽기 11번째 T2 커밋 응답 중 ‘이전’ | 10번째의 확정 재고 9, 미확정 8, T2 잠금과 행에 붙은 실선은 맞다. 회색 응답 점선은 취소한 커밋의 DB 공통 포트에 계속 붙어 있다. 같은 10번째를 직접 열면 행 포트에서 시작한다. 두 폭에서 정지 상태로 비교했다. |
| 6 | 메모리와 Git · 수동 한 단계 재생을 정지했다가 이어서 재생 | 메모리의 7번째 B에서 재개하면 8번째 E까지 자동으로 시작된다. Git도 3번째 add에서 재개하면 4번째 커밋이 자동으로 시작된다. 마지막 사건 도중 멈추면 메모리는 ‘다시 재생’, Git은 ‘처음부터 재생’이라고 표시한다. 둘 다 실제로 누르면 중단한 이동을 마친다. |

320px 트랜잭션에서는 배속 버튼 오른쪽 약 13px도 패널 경계를 넘는다. 보이는 부분을 터치하면 작동했다.

## 실제 상태가 맞았던 구간

| 탐색기 | 중단한 사건과 대조 결과 |
| --- | --- |
| 프로토콜 | ICMP·SMTP·HTTPS의 이전 단계는 같은 첫 패킷과 장치로 복원됐다. IMAP 5단계에서 새 메일 알림이 노트북에 도착하기 전 멈추면 서버 3통·노트북 2통이 유지됐다. 이전인 4단계로 돌아가면 서버·노트북 2통과 서버의 메일 2 ‘안 읽음’이 직접 진입한 상태와 같았다. |
| CPU | RR 4ms에서 10→9ms와 15→14ms로 돌아가면 작업 위치, 잔여 시간, 실행 기록이 직접 진입과 같았다. 390px에서 이동 중 1×→2×, 정지 중 2×→0.5×를 적용했다. 정지한 이동의 시간은 300ms 동안 그대로였고, 재개하면 같은 위치에서 0.5×로 이어졌다. |
| 메모리 | LRU 7번째 B를 적재하는 중 되감으면 밀려났던 C와 페이지 테이블 C→F2, 완료 기록 6회가 복원됐다. 재생을 마치면 B→F2와 7회가 됐다. 마지막 B가 CPU에 돌아오기 전 정지하면 완료 기록은 9회로 유지됐다. |
| 트랜잭션 | 잠금 읽기 8번째 T2 읽기 응답을 약 650ms 멈춘 동안 읽은 값은 ‘—’로 남았다. 9가 도착한 후에 값이 바뀌었다. 11번째를 끝까지 다시 실행하면 8이 확정됐다. |
| 디스크 | FCFS 3번째 183→37에서 2×로 움직이는 헤드를 멈추고 0.5×로 바꿨다. 정지 중 각도는 유지됐고, 이전으로 돌아가면 헤드 183·누적 130, 다시 도착하면 헤드 37·누적 276이었다. 바늘 각도와 여덟 요청의 상태도 직접 이동과 일치했다. |
| Git | 9번째 충돌 비교에서 C2를 멈췄을 때 도착한 버전은 C0 한 개였다. 8번째로 돌아가 기다려도 취소한 이동이 인덱스를 바꾸지 않았다. ‘main 문장 유지’와 ‘feature 문장 선택’을 각각 끝까지 재생했다. C2 대비 변경 파일은 각각 0개와 1개였고 C3의 부모는 둘 다 C2와 C1이었다. 12번째 도중 11번째로 되감으면 선택한 파일과 인덱스, 커밋 세 개가 복원됐다. |
