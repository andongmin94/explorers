# 탐색기 학습 품질 검수

2026년 11월 11일. 여섯 탐색기의 통합 빌드를 브라우저에서 열어 아래 조작을 확인했다. 각 프로젝트의 자동 테스트 75개가 통과했다. 390px 화면에서는 디스크 단계 이동, CPU 해설 제목, 메모리 페이지 테이블, Git 해결안 선택도 확인했다.

| 탐색기 | 다시 해 볼 조작 | 확인 기준 |
| --- | --- | --- |
| 디스크 | 첫 화면에서 FCFS의 ‘3 방향 변화’를 선택한다. 초기화한 뒤 슬라이더로 같은 위치를 고른다. 재생 도중 일시정지하고 다시 끝까지 진행한다. | 53 → 98 → 183 → 37, 헤드 37, 누적 276칸, 처리 3건이 일치한다. 마지막 누적 거리는 FCFS 640칸, SSTF 236칸이다. |
| 프로토콜 | TCP의 순서가 뒤바뀐 수신과 재전송을 이어 보고 패킷을 펼친다. 새 HTTP 수업에서 마지막 단계만 실행한 뒤 수업 목록을 연다. | 중복 ACK 한 번에 붙은 SACK는 두 번째 세그먼트의 수신 범위를 나타낸다. 이 예에서는 0.052초에 송신한 첫 세그먼트의 1초 타이머가 1.052초에 만료돼 Seq 1을 다시 보낸다. 이어지는 누적 ACK는 2921이다. 마지막 단계만 마친 수업은 진행 중으로 남는다. |
| 메모리 | FIFO에서 네 번째 A까지 이동한다. 프레임의 적재·최근 접근 차례로 D가 밀어낼 페이지를 예측한 뒤, ‘다음 접근’을 연달아 누른다. LRU에서도 같은 두 접근을 본다. | D의 조회·교체·적재·접근이 끝나야 여섯 번째 A를 시작할 수 있다. FIFO는 A를 내보내 다음 A에서 부재, LRU는 B를 내보내 다음 A에서 적중이다. 열 번의 접근 후 부재·교체는 FIFO 7·4회, LRU 6·3회다. |
| CPU | RR 할당량 2ms와 5ms에서 FCFS 비교를 연다. 시작 시각에 P3의 반환 시간을 확인하고 4ms 핵심 장면을 고른다. | 2ms에서 전체 완료는 RR 20ms, FCFS 16ms다. 5ms에서는 선점 없이 두 방식의 실행 순서와 평균 응답 3ms, 평균 대기 5ms, 전체 완료 16ms가 같다. 도착 전 작업과 실행 중인 작업의 표기가 구분된다. |
| Git | 8번째 사건에서 다음 사건을 실행한다. 충돌 표식이 나타나면 ‘해결안 선택’에서 ‘main 문장 유지’를 고른 뒤 등록과 커밋을 차례로 실행한다. | C0·C2·C1의 제목이 인덱스에 한 줄씩 도착한 뒤 작업 파일에 충돌 표식이 나타난다. 해결을 등록하면 HEAD 대비 변경 파일은 0개다. C3의 부모는 C2와 C1이고 feature/title은 C1에 남는다. |
| 트랜잭션 | 재고 갱신 끝에서 사건 기록을 열고 재개된 SQL의 원래 요청을 찾아간다. 잠금 읽기와 교착 상태 시나리오의 종료 값도 비교한다. | 재고 갱신 사건 11개는 새 SQL 8개, 앱 계산 2회, 대기 후 재개 1회다. 일반 읽기에서 재고 9, 잠금 읽기에서 8이다. 교착 상태에서 T2 롤백 뒤 T1이 커밋하면 A 9·B 19, 커밋 1회·롤백 1회다. |

TCP 재전송 해설은 이 수업에서 선택한 타이머 값을 사용한다. TLS 1.3과 HTTPS에서는 ServerHello 이후 암호화되는 핸드셰이크 메시지와 예제의 평문 호환용 ChangeCipherSpec를 구분했다. [TCP 재전송 타이머](https://www.rfc-editor.org/rfc/rfc6298.html#section-5) · [TLS 1.3 호환 모드](https://www.rfc-editor.org/rfc/rfc8446.html#appendix-D.4)

프로토콜은 수정한 TCP·HTTP·TLS·HTTPS 수업을 브라우저에서 확인했고, 14개 수업의 215개 패킷 구성은 자동 검사로 확인했다. 새 프로필에서 마지막 단계만 본 HTTP 진도는 1/5였다. 이전 버전에서 이미 완료로 저장한 수업은 어떤 단계를 건너뛰었는지 구분할 기록이 없어 보존한다.
