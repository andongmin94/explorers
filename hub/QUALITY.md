# 여섯 탐색기 모바일 재생 검수

해설과 기록 표를 가리고 통합본을 터치로 조작했다. 판단 기준은 출발지와 도착지가 보이는지, 어떤 대상이 왜 바뀌었는지 장면 안에서 구별되는지, 카드가 다른 대상의 이름이나 값을 가리지 않는지였다. 지난번의 FTP·CPU FCFS 빈 상태·Git 브랜치 전환보다는 다른 사건과 모바일 조작 뒤의 화면 위치를 우선했다. [실제 재생 프레임 여섯 장](scene-comparison.jpg)

Chromium 모바일 에뮬레이션의 세로 화면에서 기본 배속으로 재생했다. 주로 390×844와 320×568을 사용했고, 프로토콜의 좁은 화면은 320×690이었다. 퀴즈 복귀는 해설을 가리지 않은 360×740·390×844에서도 실제 확인 버튼을 눌러 대조했다. 장면 내부의 이름·방향·수치는 그대로 뒀다. 실기기·초심자 사용성 시험은 아니다.

## 수정 우선순위

| 순위 | 어디서 재현되는가 | 관찰과 권장 수정 |
| --- | --- | --- |
| 1 · P1 | 메모리 FIFO 8번째 E 교체, 트랜잭션의 일반 읽기·잠금 읽기·교착 예측 → 실제 확인 | 퀴즈가 닫혀도 스크롤은 하단에 남는다. 360·390px에서 FIFO 교체, 일반 읽기의 T2 쓰기 재개, 교착 롤백은 추가 스크롤 없이는 **처음부터 끝까지 그림이 0px** 보였다. 잠금 읽기의 T2 재개도 390px에서 화면 밖에서 시작했다. 같은 조작으로 디스크는 그림으로 돌아왔다. 확인 버튼이 교체할 프레임 또는 DB를 먼저 보여준 다음 재생하도록 맞추는 것이 우선이다. |
| 2 · P1 | CPU · RR 1ms, 7→8ms / 320×568 | ‘다음’ 버튼을 화면 맨 아래에 맞추고 누르면 P2의 SSD 복귀는 보이지만 마지막 P3의 준비 큐→CPU 배정 카드는 화면에 최대 1px만 보인다. 390×844에서는 P2 복귀→P1 시간 만료→P3 배정이 모두 보인다. 짧은 화면에서는 조작 직후 배정 경로가 시야에 들어와야 한다. |
| 3 · P1 | 트랜잭션 · 교착 1·2번째 시작, 10번째 커밋 | T1의 시작 카드는 행 A 잠금 포트, T2 시작은 행 B 포트로 간다. 마지막 커밋도 행 A로만 들어가지만 A와 B가 함께 확정된다. 행을 선택하는 쓰기만 행별 경로로 보내고, BEGIN·COMMIT은 DB 공통 입구로 보내면 잘못된 인과를 없앨 수 있다. |
| 4 · P2 | 프로토콜 · DNS 4단계 / 320·390px | 권한 서버의 응답 카드가 리졸버에 도착하면서 장치와 주소 `8.8.8.8` 전체를 덮는다. 응답 본문은 각각 약 4.3·5.2 CSS px로, 확대 없이 주소·TTL을 읽기도 어렵다. 패킷 표식은 경로 위로 움직이고 응답 내용은 수신 장치 옆에 남기는 방식이 맞는다. |
| 5 · P2 | Git · C2 커밋과 마지막 C3 병합 커밋 / 320·390px | 스테이징→저장소 이동 카드가 관계없는 작업 파일을 가로지른다. 같은 통로에는 반대 방향의 `git add ↓`가 남는다. 세로 화면에서는 commit 경로를 파일 옆으로 빼고 현재 동작의 화살표만 강조하는 편이 명확하다. 320×568에서 병합이 끝나면 C3·부모 두 개는 보이지만 그래프의 `HEAD → main` 글자는 화면 위에 남는다. |
| 6 · P2 | 디스크 SSTF 5번째, 트랜잭션 교착 6번째 / 320·390px | 디스크에서는 14→98을 선택한 뒤 약 0.77초에 98 카드가 아래 대기 중인 124를 덮는다. 교착에서는 T2의 ‘A 쓰기’ 카드가 기존 T1의 B 잠금 대기 표시를 통과한다. 데이터는 그대로인데 다른 대상이 사라져 보인다. 출발 카드가 큐 바깥으로 먼저 빠지고, 대기 관계도 옆으로 요청을 보내도록 경로를 고치는 것이 좋다. |

**뒤이은 가독성 수정.** 320px에서 메모리의 F1 카드가 ‘접근 완료’ 끝 13px을 가리고 ‘조회’도 RAM 제목 상자와 겹친다. CPU RR 13ms의 P1 ‘입출력 2 ms 남음’은 카드 밖으로 약 27px 넘쳐 그림 가장자리에서 잘린다. 교착 상태의 ‘T2 보유’는 ‘보 / 유’로 갈라진다. 메모리 첫 A 적재에서는 390px에서도 움직이는 사본이 SSD의 B·C를 잠깐 덮는다.

**추가 학습 단서.** TLS 3단계의 카드가 ‘암호화됨’인 것은 맞고 신뢰 루트 문구도 뜬다. 그러나 인증서를 *누가 어떻게 확인했는지*는 그림만으로 구분하기 어렵다. 수신 후 클라이언트에서 인증서 사슬을 연결해 주면 검증을 전송과 구별할 수 있다. DNS 5단계의 캐시 표식은 리졸버에만 남아 클라이언트 쪽 캐시는 그림에서 확인할 수 없다.

## 이번에 재생한 구간과 읽힌 부분

| 탐색기 | 구간 | 그림만으로 구별된 변화 |
| --- | --- | --- |
| 프로토콜 | DNS 4·5, TLS 3, IP 5, HTTP 5단계 | IP 회신은 라우터를 통과하며 공인 목적지가 사설 목적지로 바뀐다. HTTP 마지막은 노트북 확대, 주소 확인 표시, 페이지 표시가 이어져 완료가 명확하다. |
| CPU | RR 1ms의 복귀·시간 만료·재배정, 13ms 유휴, 완료 | 390px에서는 같은 시각의 세 이동이 순서대로 보인다. 13ms에는 완료한 P2·P3와 SSD에서 대기하는 P1을 구별할 수 있다. |
| 메모리 | FIFO 첫 A 부재, 3번째 C의 빈 F2, 8번째 E 예측, 10번째 B 적중 | 빈 프레임을 먼저 선택하고 SSD에서 C를 가져온다. 마지막 B는 SSD를 거치지 않고 F2에 그대로 남으며 마지막 사용 시점이 10으로 바뀐다. |
| 트랜잭션 | 교착 시작·두 잠금 대기·탐지·롤백·마지막 커밋, 잠금 읽기 유무에 따른 T2 재개 | 그림이 보이는 위치에서는 ‘순환을 발견함’과 ‘한쪽이 롤백돼 잠금이 풀림’이 서로 다른 사건으로 읽힌다. |
| 디스크 | FCFS 2·4·7번째, SSTF 1·5·8번째 | SSTF 5번째는 98까지 84칸과 122까지 108칸이 동시에 표시돼 선택 이유가 보인다. FCFS 7번째는 124→65 도착 뒤 누적 579→638, SSTF 마지막은 124→183 도착 뒤 누적 236칸이다. |
| Git | main 파일 수정·스테이징·C2 커밋, ‘두 의도를 합치기’ 해결·등록·C3 커밋 | 수정만 하면 작업 파일만 바뀌고, 등록해야 스테이징이 같아진다. 병합 완료 뒤 C2와 C1이 모두 C3에 연결되고 feature/title은 C1에 남는다. |
